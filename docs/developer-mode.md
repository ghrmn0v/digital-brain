## Developer Mode

When enabled, Core Brain understands the developer's repository and current
development context, detects potential bugs/issues, explains them, proposes
actions and emits structured Brain Events. **Core Brain is the intelligence;
Fly only visualizes.** Fly does not detect bugs, reason, explain, or make AI
decisions. Product (Ayxan) owns permissions, action execution, UI, connectors
and external integrations.

```
Developer → Product / Repository Context → Core Brain
  (memory · context · people · reasoning · intent · action planning · learning)
  → Brain Events → Product / Fly
```

## Brain → Product boundary (action permission)

```
Core Brain  →  Proposal (Pure data, ProposedAction)  →  Permission  →  Product executes
```

- Brain **proposes** actions (e.g. `code.fix`, `run_tests`, `deploy`). It never
  executes external effects: no automatic Git push, no automatic deployment,
  no automatic external messages, no destructive action.
- Proposed actions are pure data (`ProposedAction` has no execution surface).
- `requested_permission_level` is REQUESTED, never granted, by the Brain.
- Execution outcome returns as `Feedback` (`source=product`) so the Brain learns.

## Brain → Fly event flow

Core Brain emits typed `BrainEvent`s (`contracts/brain_events/events.py` —
open, additive enum). The developer-mode event pipeline (Phase 6 builds the
emitters):

```
developer.bug_detected
    ↓
developer.fix_proposed
    ↓
developer.test_result
    ↓
developer.review_finding
    ↓
developer.deploy_proposed
    ↓
feedback  ↓  learning
```

Not every event must be present; each is independently useful. Explanations in
events are generated by Core Brain (short enough for Fly's thought bubble);
Fly renders them and moves to the relevant file/line.

## Supported developer events

Planned set (added to `BrainEventType` when Phase 6 lands):

| event type | payload essentials |
|---|---|
| `developer.bug_detected` | repository, file, line, column?, title, message/explanation, severity, confidence, correlation_id |
| `developer.fix_proposed` | affected file, affected lines, explanation, proposed change, confidence, required permission |
| `developer.test_result` | pass/fail/skip/error counts + reason summary, affected files |
| `developer.review_finding` | file, line, severity, explanation, confidence, category |
| `developer.deploy_proposed` | environment, repository, reason, test status, risk/confidence, requested permission |

## MVP limitations (current, Phase 3 done)

- Fallback/heuristic understanding is keyword-based with low, honest
  confidence — it is a deterministic stand-in, not an AI.
- No semantic (vector) search yet; `MemoryService.retrieve_relevant_memories()`
  remains the deterministic retrieval path.
- No bug detection / reasoning / action planning yet (Phase 6).
- No feedback/learning loop yet (Phase 7).
- No real provider configured; `heuristic` is the default so the MVP is
  reproducible offline. Register a real provider via `register_provider(...)`.
