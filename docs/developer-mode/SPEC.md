==================================================
PROJECT VISION
==============

We are building an AI Developer Companion with a persistent Core Brain.

When Developer Mode is enabled, Core Brain should understand a developer's codebase and development context, detect potential bugs/issues, explain them, reason about possible fixes, propose actions, and emit structured Brain Events.

The Fly is only the visual representation/interface.

Core Brain is the intelligence.

Fly does NOT:

* detect bugs
* reason about bugs
* generate explanations
* make AI decisions

Core Brain does all of those.

The Product layer owned by Ayxan handles:

* permissions
* action execution
* UI
* connectors
* external integrations

Fly owned by Sadeddin handles:

* visualizing Brain Events
* moving to relevant code location
* displaying Core Brain's explanation

Architecture:

Developer
↓
Product / Repository Context
↓
Core Brain
├── Understanding
├── Memory
├── Context
├── People / Preferences
├── Reasoning
├── Intent
├── Action Planning
└── Learning
↓
Brain Events
↓
Product / Fly

HACKATHON-SPECIFIC GOAL
=======================

The main Developer Mode workflow must support:

1. Repository/code context enters Core Brain.
2. Core Brain understands relevant code.
3. Core Brain detects a potential bug.
4. Core Brain identifies:

   * repository
   * file
   * line
   * optional column
   * severity
   * title
   * explanation
5. Core Brain emits:

developer.bug_detected

6. Fly receives the event and moves to the relevant line.
7. Fly displays the title/explanation generated by Core Brain.
8. Core Brain can propose a fix.
9. Product asks for permission.
10. Approved action can be executed by Product.
11. Tests can be run.
12. Core Brain can interpret test results.
13. Core Brain can perform a lightweight code-review analysis.
14. Core Brain can propose deployment.
15. Deployment remains permission-controlled.
16. Feedback is sent back to Core Brain.
17. Core Brain learns useful preferences/signals.

PHASE 3 — LLM GATEWAY + UNDERSTANDING
=====================================

Implement a provider-independent LLM abstraction.

Do NOT hardcode business logic directly into one provider.

Create a clean gateway similar conceptually to:

LLMGateway
├── understand(...)
├── analyze(...)
└── generate_structured(...)

The exact API should fit the existing architecture.

The gateway must support:

* timeout
* errors
* invalid structured output
* provider abstraction
* deterministic fallback where reasonable

Provider selection must be configurable.

Do not assume a specific provider unless the project already has an explicit decision.

Create structured Understanding results.

At minimum support:

* entities
* intent
* topics
* salience
* confidence
* summary
* relevant code concepts when analyzing developer context

Do not allow arbitrary unvalidated LLM output to enter Memory.

All LLM output must be validated.

==================================================
BRAIN EVENT
===========

When a potential bug is detected, emit a structured Brain Event.

Primary event:

developer.bug_detected

It must contain enough information for Fly/Product to act:

* event ID
* repository
* file
* line
* optional column
* title
* message/explanation
* severity
* confidence
* correlation ID
* source/context information where useful

The explanation must be generated by Core Brain.

Fly must not generate it.

==================================================
EXPLANATION
===========

Core Brain should be able to generate a developer-friendly explanation.

Example:

Title:
Possible null reference

Message:
user may be undefined before accessing user.email.
If getUser() returns null, this line can throw at runtime.

Keep explanations concise enough for Fly's thought bubble.

Detailed explanation can be available through Product UI.
