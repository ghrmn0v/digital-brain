## The final product will have BOTH: 💻 PC and 📱 Mobile

Core Brain is the **shared intelligence layer** for both platforms. Core Brain
**MUST remain completely platform-independent** and must NOT contain: mobile UI
logic, PC UI logic, Electron-specific logic, React Native-specific logic, or any
platform-specific presentation logic. Clients consume Core Brain through stable
APIs/contracts/events.

```
                🧠 CORE BRAIN
                     │
          Intelligence / Memory / Context
                     │
            APIs / Events / Data
                     │
         ┌───────────┴───────────┐
         │                       │
      💻 PC                    📱 Mobile
```

## Shared Brain capabilities (single Core Brain, both clients)

Memory · Context · Understanding · AI reasoning · People intelligence ·
Relationship understanding · Semantic search · Intent understanding · Action
planning · User preference learning · Importance learning · Feedback
interpretation · Long-term personalization · Event understanding · Developer
intelligence.

Future APIs/events MUST be designed so that **either client can consume
appropriate Brain information**.

## Voice / microphone (shared capability)

Mobile supports microphone input, voice interaction, Brain responses; PC **may
too**. Core Brain owns the **intelligence/interpretation layer, NOT the
device-specific microphone implementation**. The client captures audio/input and
sends it through the Product/API layer; Core Brain receives **normalized input**
and returns **structured intelligence/results**. No mobile or PC microphone
libraries in Core Brain.

## Developer Mode (PC-only product capability, Brain stays platform-neutral)

Developer Mode is PC-only; Core Brain still owns its intelligence: developer
context understanding, code understanding, bug detection, bug explanation, fix
proposals, test interpretation, code review findings, deployment-related
reasoning, developer events. Core Brain must NOT assume it runs on a PC — it
only produces **platform-independent developer data/events**.

## Developer information (NOT PC-only)

Developer information generated by Core Brain may be consumed by BOTH clients:
bug detected, bug title, explanation, repository, file, line, column, severity,
confidence, fix proposal, test result, code review finding, deployment status.

- 💻 PC flow: Repository → Developer Mode → Core Brain → `developer.bug_detected`
  → PC UI / Fly.
- 📱 Mobile flow: Core Brain developer event/data → Mobile Product layer →
  notification / developer-information view. Mobile does NOT activate Developer
  Mode, does NOT perform local repository analysis, does NOT render Fly.

## Developer events — keep platform-independent

`developer.bug_detected`, `developer.fix_proposed`, `developer.test_result`,
`developer.review_finding`, `developer.deploy_proposed` are **Brain-level
events**. Event contracts must NOT embed React, Electron, React Native, mobile
UI components, or Fly implementation details — only the data consumers need to
present the information.

Naming reconciliation (Phase 8 Slice 1): the roadmap prose above previously
listed `developer.deploy_status` — the authoritative SPEC.md and the implemented
contract both use **`developer.deploy_proposed`**, so the code name is NOT
renamed; this prose now matches the contract. `developer.explanation` is not a
separate event type: explanations live inside the `developer.bug_detected` /
`developer.fix_proposed` payloads.

## Fly (PC-only, Connectome layer)

Core Brain does NOT implement Fly and does not directly control another
developer's UI. Flow: Core Brain → `developer.bug_detected` → Connectome /
Product → 💻 Fly. Mobile may consume the same underlying developer information
but does not render Fly.

## Permissions and actions — unchanged in this architecture

Brain proposes; Brain does NOT directly execute external actions. Product layer
handles permission, user confirmation, execution, connector interaction — the
same on PC and Mobile.

## Platform-independent API design (holds for ALL future Core Brain work)

Stable contracts · structured events · structured results · user isolation ·
traceability · correlation IDs · versioned contracts · platform-independent
data. Avoid APIs that assume desktop/mobile/Electron/React Native/local
filesystem/local UI state — unless explicitly a developer/backend capability and
kept separated from presentation.

## Phase 7 — Feedback + Learning + Personalization (complete)

- Added `core/learning/`:
  - `exceptions.py` — `LearningError` / `LearningValidationError`.
  - `models.py` — `SignalKind` (accepted/rejected/ignored/corrected/successful/
    unsuccessful), `LearningSignal`, `StoredFeedback`, `TopicAffinity`
    (positive/negative/ignored counts, positive rate, direction),
    `PreferenceEvidence` (weighted belief), `LearningStatus` (bounded per-user
    aggregate), `AssistanceProfile`/`AssistanceNudge`, `LearningLimits`.
  - `interpreter.py` — `FeedbackInterpreter`: deterministic Feedback → signal.
    Order: `metadata["signal"]` override → label → OUTCOME/REWARD value → numeric
    value. Unreadable records raise (never invent). Strength scaled by value;
    delta_importance positive `+0.05·s` / negative `−0.06·s` / ignored `0`;
    topic from metadata or `suggestion:<action_type>`; preference hint +
    `tests_were_green` extracted predictably.
  - `ports.py` — `LearnerMemory` / `LearnerMemoryWriter` / `LearnerMemoryUpdater`
    (all satisfied by `MemoryService`) + `LearningStateRepository`.
  - `state.py` — `SqliteLearningStateRepository` (single table, one row per
    user, JSON aggregates); a swap seam for a future learning store.
  - `learning.py` — `LearningEngine`: `record_feedback` (durable OBSERVATION
    memory trace + aggregate update), `feedback_history` (replay), 
    `learning_status`, `personalization_profile`. Explicit rules only:
    repeated acceptance → preference (via People Intelligence supersession);
    repeated rejection → `avoid:<topic>` preference; acceptance while tests
    green → `fix-accepted-after-tests`; memory-targeted feedback adjusts that
    memory's importance (bounded).
  - `personalization.py` — `PersonalizationEngine` → `AssistanceProfile`:
    explanation preference surface, top/avoid affinities, deterministic nudges.
- Design decisions:
  - NO fake ML: every number is an honest counted signal with bounded strength.
  - Learning owns no storage of raw feedback — traces live in Memory Engine
    (retrievable by future reasoning); aggregates in the state repo; learned
    preferences feed Context/Raisonning via the existing preference pipeline.
  - Strict user isolation (learning state and traces never leak across users).
  - Platform-independent by construction (no UI / device / desktop hooks).
- Tests: 26 new (`test_learning.py`, `test_personalization.py`,
  `test_feedback_loop.py`). The loop E2E uses the Phase 6 pipeline: propose →
  product rejects/accepts → signal over correlation id → learned preference +

### Phase 5C — Person Naming and Deterministic Identity Resolution

- Fixes a real gap found while building the TypeScript client: nothing in the
  ingestion path ever recorded a person name, so `people_summary` always
  returned `name=null` and name-based identification could never fire for
  ingested data.
- Additive contract change: `Subject.person_name` (optional, ≤200 chars) in
  `contracts/events/source_event.py`. Optional field ⇒ v1 stays v1;
  `contracts/schemas/brain-api.v1.json` regenerated and the TypeScript client's
  `Subject` type updated.
- Naming: when an event names its subject next to a resolved `subject.person_id`,
  `_candidate` records `metadata["person_name"]`. A name without a person id is
  never stored as one.
- `PeopleIntelligence.resolve_person(user_id, name, *, aliases, source)` →
  `PersonResolution`:
  - exact normalized name/alias match reuses the existing person
    (`created=false`);
  - a name already used by two people returns `person_id=None`,
    `ambiguous=true` and both ids in `candidates` — **never merged**, nothing
    written;
  - an unknown name mints a deterministic `per_<slug>_<sha256(user+name)[:8]>`
    id and writes one identity memory (`kind="person_identity"`,
    `person_key` conflict key so re-recording supersedes, `durability="durable"`,
    `source.provider="people"`), so the same name always converges instead of
    forking a second person.
- Token overlap stays a *mention* (`identify_people`), never an identity; the
  only comparison used for resolution is the normalized exact name.
- `BrainService.ingest` resolves a named-but-unidentified subject before
  ingestion, so the memory is linked to a real person; a new identity emits
  `person.created` (new `BrainEventDispatcher.person_created` /
  `BrainEventEmitter.person_created` methods for the already-catalogued event
  type). An explicit `subject.person_id` is never re-resolved.
- `people_summary` keeps an identity-only person visible with `mention_count=0`
  and never counts the identity record as a mention.
- Bounds: `PeopleLimits.max_person_aliases=8`, `max_person_name_length=200`;
  invalid input raises `PeopleValidationError`; a read-only People Intelligence
  refuses to resolve.
- `PersonResolution` invariants are enforced with a Pydantic
  `model_validator(mode="after")` — `__post_init__` is not invoked by
  Pydantic v2 and was silently dead.

- `Json.java` — minimal strict JSON reader/writer over `Map`/`List`/`String`/
  `Double`/`Boolean`/`null`, since the JDK ships no JSON API and adding Jackson
  would break the zero-dependency property. Deterministic key order, control
  character and escape handling, rejection of trailing content, unterminated
  strings and non-finite numbers.
- `BrainRequests.java` — the shared rules: request-id minting, the
  `ApiRequest` envelope, `user_id` injection, the `ApiResponse` invariants and
  the event consumer rules (dedupe by `BrainEvent.id` in a bounded window,
  per-user filter, `correlation_id` grouping).
- `BrainHttpClient.java` — `POST /v1/brain` and `GET /health` via
  `java.net.http.HttpClient`; `request(...)` returns the envelope, `call(...)`
  returns the result or throws `BrainApiException`.
- `BrainWebSocketClient.java` — `/v1/brain?user_id=…` via
  `java.net.http.WebSocket`, with responses correlated by request id (a pending
  future is registered before the frame is written), a response timeout, live
  events through `onEvent`, and a clean close that fails in-flight requests.
- `BrainClient.java` + `SelfCheck.java` — entry point and a dependency-free
  self check (`main`) that exercises JSON round trips, escaping, event dedupe
  and filtering, correlation ids, the 17-method table and identity injection,
  plus an optional live round trip against a running Core.
- **Verification status (honest): this client was NOT compiled or executed
  here.** The environment has a JRE only — no `javac`, no `jdk.compiler` module,
  no Maven — and installing a JDK is out of scope. What *is* mechanically
  verified is `tests/test_java_client_parity.py` (12 tests): the Java method
  table equals `ApiMethod` and the schema bundle in order, the endpoint paths and
  API version match the Core transports, the error codes it branches on are
  canonical, no source calls a method outside the registry, there are no
  third-party imports and `pom.xml` declares no dependencies. Manual review also
  found and fixed two real defects before delivery: a `CompletableFuture`
  assigned to a `WebSocket` field in `connect()`, and a response-correlation
  race in `call()`. Treat the client as a reviewed first draft: a developer with
  a JDK must run `mvn -q package` and `SelfCheck` before relying on it.

### Phase 8 (Slice 9) — Public Error Mapping and Preference Precedence Fixes

Two genuine bugs found by the final audit, both fixed with regression tests.

- **Input errors leaked as `internal_error` (10 public paths).** People and
  Learning own the detailed input rules, but their exceptions were not mapped at
  the service boundary, so a whitespace-only `user_id` (or preference name,
  value or `person_id`) reached clients as an opaque `internal_error` that hid
  the real reason. `preferences`, `developer_preferences`, `people_summary`,
  `people_timeline`, `resolve_person`, `record_preference`, `learning_status`,
  `feedback_history`, `personalization_profile` and the feedback path are
  affected. Fix: `_as_service_validation(...)` in `core/service/brain_service.py`
  translates `PeopleValidationError` / `LearningValidationError` into
  `BrainServiceValidationError`, which `BrainApi` already maps to
  `validation_error`. Non-validation failures are deliberately left untouched.
- **A learned preference silently overwrote an explicit user preference.**
  `_learn_preferences` writes through People Intelligence, whose conflict key is
  `<domain>:<name>` — the same key an explicit record uses, so three accepted
  signals turned an explicit `language=Rust` into `language=Python`. Fix:
  `_has_explicit_preference(...)` checks the active preference memories for the
  same conflict key without the `learned` marker, and the learned write is
  skipped. Explicit wins; the counted evidence stays visible in
  `learning_status.preference_evidence`, and a learned preference with no
  explicit counterpart is still written as before. A deliberate explicit
  re-record still supersedes.
- Tests: `tests/test_error_mapping.py` (6) and
  `tests/test_preference_precedence.py` (6) — all 10 affected methods, valid
  requests still succeeding, unknown-method routing unchanged, explicit-wins,
  evidence visibility, learned-still-lands, deliberate override, provenance on
  a learned record, and the same precedence through `BrainApi`.
